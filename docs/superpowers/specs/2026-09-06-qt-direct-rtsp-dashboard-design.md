# Qt 客户端直连 RTSP 监控工作台设计

## 1. 目标与边界

本设计只扩展 `client/qt/SmartHomeClient` 登录成功后的工作台。目标是在 Windows + Qt 5.14.2 MinGW 32 位环境中，直接预览两路已配置的 RTSP 摄像头，并为球机提供云台控制入口。

本次不修改 `server`、`common`、Reactor、ThreadPool、连接生命周期、HTTP/JSON 服务端模块、FFmpeg 服务端拉流模块或媒体包转发模块。客户端仍使用既有 TCP/TLV 登录、设备列表和录像查询链路；实时预览不经过服务端，而是由 Qt 客户端直接连接摄像头。

摄像头账号、密码和 RTSP 地址保存在 `conf/cameras.conf.example` 配置中。

## 2. 团队复用审查结论

当前 `dev-integration` 中的服务端 `ffmpeg_media_source` 负责从 RTSP/RTMP 读取压缩媒体包，服务于服务端媒体转发链路；现有 Qt 客户端没有相应的媒体包解码和显示实现，不能直接复用为本次桌面预览。

`dev-xgq` 存在独立 libVLC 样例及大体积第三方目录，但它没有接入 `SmartHomeClient` 的构建、登录或设备模型。直接合并会引入大量无关文件和部署成本，因此不作为本次实现基础。

所以本设计不会重复实现服务端拉流，而是限定为独立的 Qt 客户端播放适配层。

## 3. 技术方案

### 3.1 方案选择

采用 `QProcess + ffmpeg.exe`：每路摄像头由一个独立的 `RtspPlayer` 管理一个 FFmpeg 子进程。FFmpeg 使用 RTSP over TCP 拉取视频，将解码后的 JPEG 帧经标准输出交给 Qt；`RtspPlayer` 在所属 Qt 事件循环中异步处理字节流，向 UI 发出 `QImage` 帧信号，避免阻塞界面线程。

选择该方案的理由：当前 Windows 环境可运行 `ffmpeg.exe`，但未发现可供 Qt MinGW 32 位直接链接的 FFmpeg 头文件和导入库。用子进程不会改变现有 Qt/MinGW 链接边界，也避免引入未接入的 libVLC 目录。

后续若团队统一提供匹配的 FFmpeg SDK，可仅替换 `RtspPlayer` 内部实现，不改变 `VideoWidget`、工作台或配置接口。

### 3.2 模块边界

| 模块 | 职责 | 不负责的内容 |
| --- | --- | --- |
| `video/RtspPlayer` | 构造 FFmpeg 命令、读取 JPEG 帧、限流缓存、异常重连和状态通知 | UI 绘制、设备列表、云台指令 |
| `video/VideoWidget` | 绘制最新帧、频道名称、播放状态和错误覆盖层 | 拉流进程与网络请求 |
| `network/PtzClient` | 管理球机 HTTP 认证和云台请求；按下开始、松开停止 | 直接播放 RTSP、服务端 TCP 协议 |
| `ui/MonitoringDashboard` | 深色四宫格布局、设备树、状态栏和控制面板 | 解析 RTSP 帧、保存账号密码 |
| `conf/cameras.conf.example` | 摄像头地址、账号、密码、FFmpeg 路径 | 媒体数据解析 |

所有新增核心类在文件顶部说明中文职责，关键函数说明异步和安全设计原因。

## 4. 工作台界面

登录成功后 `MainWindow` 切换到深色监控工作台：

```text
┌──────────────── 标题、实时预览、录像查询、设备管理、时间 ────────────────┐
│ 状态/事件 │            通道 01（枪机） │ 通道 02（球机） │ 设备树      │
│            ├───────────────────────────┼─────────────────┤             │
│            │            通道 03（待接入）│ 通道 04（待接入）│ 云台控制    │
└───────────────────────────────────────────────────────────────────────┘
```

- 通道 01 使用枪机配置，通道 02 使用球机配置。
- 通道 03、04 明确显示“等待接入”，不伪造视频源。
- 设备树显示配置摄像头及通过现有设备列表协议返回的设备数据。
- 选中枪机时，云台控制区禁用并说明“当前设备不支持云台控制”。
- 选中球机且认证成功后，显示八方向控制、变倍、聚焦、光圈和速度；按下按钮发送开始指令，松开/离开按钮发送停止指令，防止持续移动。
- 左侧仅展示真实客户端事件，例如“已连接”“正在重连”“视频流已断开”，不构造虚假的报警或人脸识别数据。

## 5. 配置、安全与运行行为

新增 `conf/cameras.conf.example`，包含枪机/球机的真实 RTSP 地址、账号和密码。

配置字段包括：枪机/球机别名、RTSP URL、摄像头 Web 地址、设备类型、FFmpeg 路径和是否启用自动预览。程序优先读取环境变量指定的本地配置路径，再读取客户端目录下的 `conf/cameras.local.conf`。

FFmpeg 进程采用 RTSP TCP 传输，标准输出仅保留有限大小的帧缓冲；若输出异常、进程退出或十秒看门狗超时，玩家进入“重连中”状态并以退避定时器重启。关闭工作台、注销或应用退出时必须终止并等待子进程退出，避免遗留 FFmpeg 进程。

## 6. PTZ 设计

`PtzClient` 使用 Qt Network 直接访问球机网页接口。先进行只读认证/能力探测，再允许用户触发实体动作。云台请求只由用户对界面按钮的按下、释放操作触发，不在程序启动、重连或测试中自动移动摄像头。

已确认设备网页接口包含 PTZ 基础配置与控制端点；实际认证令牌和控制参数将以抓取到的设备公开前端契约为准。实现中把端点、认证和动作参数集中在 `PtzClient`，便于同型号设备接口差异时只改该类。认证失败、控制响应异常或选择枪机时，控件保持禁用并显示清晰原因。

## 7. 数据流与错误处理

```text
本地摄像头配置 → MonitoringDashboard → RtspPlayer → ffmpeg.exe → QImage → VideoWidget
球机选择/按键   → PtzClient → 摄像头 Web API
既有登录        → UserService → MainWindow → MonitoringDashboard
既有设备列表    → UserService → DeviceModel → 设备树
```

缺少本地配置、FFmpeg 不存在、RTSP 认证失败、摄像头不可达、PTZ 认证失败均只能影响对应频道或控制面板，不能阻塞已登录界面或终止已有 TCP 登录连接。

## 8. 测试与验收

不依赖真实摄像头的自动化测试：

1. `RtspPlayer` 命令行构造、无效配置、子进程错误和 JPEG 帧边界解析。
2. `VideoWidget` 在无帧、有效帧、错误状态下的绘制状态。
3. `PtzClient` 使用本地假 HTTP 服务验证认证与开始/停止请求构造；不向实体摄像头发送动作。
4. `MonitoringDashboard` 结构测试：四个频道、两条已配置通道、设备树和球机/枪机控件状态。
5. Qt 5.14.2 MinGW 32 位重新配置、构建和 CTest。

真实环境验收由用户在 Windows 客户端完成：登录成功后两路画面出现；停止服务或断网时对应频道显示重连；点击球机方向键并松开后摄像头仅在按住期间运动。真实 PTZ 移动属于物理设备行为，必须在用户明确操作时验证。

## 9. 非目标

本次不实现服务端媒体转发、FFmpeg C API 解码、录像播放解码、云端转码、云台控制服务端代理、摄像头凭据数据库保存、告警算法或虚假告警内容。
